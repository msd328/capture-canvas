# Bounded native OIDC JWKS resolution — 2026-08-03

## Scope

This batch adds the public-key retrieval and key-selection boundary required before
Recorder can cryptographically verify a Supabase OpenID Connect ID token.

The resolver fetches only the compile-time-pinned JWKS URI, validates a tightly bounded
RS256/ES256 key set, parses the ID-token header strictly, and selects one exact key by
`kid` and `alg`. It does not verify the token signature or claims, establish a session,
persist tokens, call `/api/v1/me/access`, or expose any authentication material to the
WebView.

## Implemented

- Added a dedicated bounded Rustls JWKS client using the existing Reqwest dependency.
- Disabled redirects, retries, runtime/system proxy discovery and automatic response
  decompression.
- Applies bounded JWKS transport deadlines:
  - five-second connection timeout;
  - five-second per-read timeout; and
  - ten-second total request deadline.
- Requires the final response URL to equal the compile-time-pinned JWKS URI exactly.
- Accepts only HTTP 200 and one `application/json` content type with no parameter other
  than optional UTF-8 charset.
- Rejects compressed responses and duplicate, malformed or declared-oversized content
  lengths.
- Enforces a 64 KiB streamed response ceiling.
- Uses a five-minute in-memory public-key cache.
- Performs one forced JWKS refresh when an ID-token `kid` is absent from the current
  cache, supporting bounded signing-key rotation without unbounded retries.
- Rejects empty key sets and key sets containing more than eight keys.
- Rejects unknown or duplicate JWKS fields through strict Serde structures.
- Rejects duplicate `kid` values.
- Accepts only:
  - RS256 with an RSA public modulus of 2048–4096 bits and a bounded odd exponent; or
  - ES256 with the P-256 curve and exact 32-byte X/Y coordinates.
- Rejects mixed key-type parameters, HS256, unsupported curves, non-signing use,
  unapproved key operations, padded/non-Base64URL components and oversized values.
- Strictly parses the ID-token JOSE header:
  - exactly three compact-JWT segments;
  - bounded Base64URL header;
  - only `alg`, `kid` and optional `typ` fields;
  - `typ`, when present, must be `JWT`;
  - `alg` must be RS256 or ES256; and
  - `kid` must be bounded visible ASCII.
- Selects only a key whose exact `kid` and approved algorithm match the header.
- Added unit coverage for valid RSA/P-256 sets, duplicate `kid`, unapproved algorithm,
  unknown fields, mixed key parameters, exact key selection, algorithm mismatch,
  duplicate JOSE fields and prohibited remote-key headers such as `jku`.
- Added path-, key- and token-free `AuthHealth` diagnostics for cache hit/refresh,
  fetch, response framing, parse and key-selection outcomes.

## Deliberately not implemented

- Cryptographic RS256 or ES256 signature verification.
- SHA-256 digest calculation for the JWS signing input.
- Strict ID-token claim parsing.
- Issuer, audience/client ID, subject, expiration, issued-at, not-before, auth-time or
  nonce validation.
- Connecting the unverified token exchange result to this resolver.
- Creating a verified native identity or session.
- Persisting or rotating refresh tokens.
- Calling `/api/v1/me/access` from the desktop.
- React AuthGate, payment routes or native entitlement enforcement.

## Dependency and lockfile note

No new Rust crate was added in this batch. The implementation intentionally reuses the
existing Reqwest, Base64, Serde and Tokio dependencies.

The repository currently does not contain a committed `Cargo.lock`, while
`scripts/windows-local-check.ps1` invokes Cargo with `--locked`. The previous bounded
transport batch changed `Cargo.toml`, so a clean checkout cannot be considered
reproducible until a lockfile generated by Cargo is reviewed and committed. This batch
does not claim to resolve that pre-existing validation issue.

## Security impact

```text
Security impact:
Added a bounded trust-key retrieval boundary and exact signing-key selection, reducing
remote-key substitution, algorithm confusion, duplicate-key ambiguity and unbounded
key-rotation retry risks before cryptographic token verification is introduced.

Data accessed:
The compile-time-pinned JWKS URI, the provider's public signing-key document, and the
unverified ID-token header when the private resolver is called in a future batch.

Data written:
A five-minute in-memory cache containing public signing keys and repository
source/documentation only.

Network communication added:
A crate-private HTTPS GET capability to the compile-time-pinned JWKS URI. No current
Tauri command, callback worker or frontend path invokes it.

New permissions/capabilities:
None.

New dependencies:
None.

External processes:
None.

Untrusted inputs:
JWKS HTTP status, headers, declared size, streamed bytes, JSON object fields, public-key
parameters, and the unverified ID-token JOSE header. All are bounded and strictly
validated before key selection.

Validation added:
Rust unit coverage for accepted RS256/ES256 key structures, duplicate kid rejection,
algorithm and key-type mismatch, strict unknown-field handling, exact key selection,
and rejection of duplicate or externally directed JOSE headers.

Secrets involved:
None in the JWKS document. The future input ID token is sensitive and remains native;
the current resolver never logs or serializes the token, header, kid, endpoint or public
key components.

Security tests completed:
Static visibility review confirms the resolver is crate-private and absent from the
Tauri invoke handler. Static transport review confirms pinned HTTPS destination, no
redirect, no retry, no runtime proxy, strict JSON framing and bounded body handling.
Compilation, rustfmt, unit execution and configured-provider runtime tests remain
pending.

Remaining risks:
Public-key selection is not signature verification. An unverified ID token must still
never create a session. The following batch must use a maintained cryptographic
implementation for RS256/ES256, verify the complete signed token and claims, and fail
closed on every mismatch. Provider compatibility with the strict JWKS field set and
clean-checkout Cargo lockfile behavior require Windows validation.
```
